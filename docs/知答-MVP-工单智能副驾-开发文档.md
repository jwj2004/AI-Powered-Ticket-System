# 「知答」MVP — SaaS 售后工单智能副驾 · 最小可用版开发文档

---

## 一、第 0 阶段：ROI 验证（0.5–1 天，**不写业务代码**）

这一步是整个项目的刹车。**不通过就不开发，最大损失是一天。**

### 1.1 要从历史工单系统拉的数

用过去 1–2 个月的真实工单数据，填下面这张表（导出 CSV 即可，不用写程序）：

| 指标 | 怎么数 | go 阈值 | 不达标怎么办 |
|------|--------|---------|--------------|
| 月工单量 | 近两月平均每月工单总数 | ≥ 100 张/月 | <100：只做"错误码速查表"单页，不上 AI 草稿 |
| 重复问题占比 | 同一错误码/同一现象出现 ≥2 次的工单占比 | ≥ 40% | <40%：问题太个性，RAG 帮不上忙，放弃 |
| 高频错误码数量 | 出现 ≥3 次的不同错误码个数 | ≥ 30 个 | <30：错误码库没肉，P0-1 价值有限 |
| 一线坐席数 | 实际处理工单的人头 | ≥ 3 人 | <3 人：规模效应不够，口头 SOP 更划算 |
| 平均处理时长 | 随机抽 20 张已解决工单算 | 记录基线 | 这个数是上线后算账的分母 |
| 数据可导出性 | 能不能拿到脱敏后的历史工单+解决方案 | 能 | 不能：无法冷启动，先解决数据导出再谈开发 |
| 主管运营意愿 | 有没有人愿意每周 1 小时看数据 | 有 | 没有：半年后知识必烂，先找人 |

### 1.2 决策

- **七项全部达标** → 进入第二阶段开发（5 天）。
- **月工单量或重复问题占比不达标** → 不做 AI 副驾，改成维护一个人工维护的错误码速查 Notion/Confluence 页面即可。
- **其他单项不达标** → 按 1.1 表"不达标怎么办"列裁剪后再进开发。

> 这一步产出一张《ROI 验证记录表》，附上原始数字。没有这张表，后面所有"省了多少时间"都是空口无凭。

## 二、定位与边界

### 2.1 一句话定位

只服务企业内部售后一线的**浏览器浮层**：不离开工单系统，按快捷键唤起，粘贴客户原话，返回**带来源引用**的错误码释义、历史解法和对外答复草稿；证据不足就明说"没把握"，绝不硬编。

### 2.2 三条铁律

1. **不另起工作台**：终态是浏览器浮层/Tampermonkey 脚本附着在现有工单页面，一线不切换系统。
2. **无引用不输出结论**：检索不到相关证据时，只说"我没找到可靠依据，建议转二线"，不编话术。
3. **冷启动用真数据**：错误码库人工填准，历史工单脱敏导入，**禁止用编造的演示数据**。

## 三、这版做什么 / 不做什么

### 3.1 第一版只做两个 P0

| 编号 | 功能 | 单次收益 | 为什么是它 |
|------|------|----------|-----------|
| **P0-1** | 错误码/配置项秒查 | 每天几十次，省 1–2 分钟 | 结构化、量小、人工填最划算，是建立信任的第一颗钉子 |
| **P0-2** | 粘贴客户原话 → 答复草稿 | 每张单省 3–8 分钟 | 核心价值所在；薄版，只给"证据片段 + 话术骨架" |

配套只做一块：**客户上下文**（租户版本、开通模块、最近一次变更），用于草稿里自动带上"贵司当前版本为 X"这类个性化句子。

### 3.2 明确这版不做（及原因）

| 原 v2 功能 | 这版决定 | 原因 | 什么时候做 |
|-----------|---------|------|-----------|
| 诊断面板四块一次聚合 | **不做** | 一次聚合要 8 秒，违背浮层秒开体验；先只返回草稿所需信息 | 第二版，且仅当浮层日均使用 ≥200 次 |
| 相似工单"相似度×解决效果"排序 | **降级** | 作为草稿的证据来源之一列出 top3，不做复杂排序算法 | 第二版 |
| Runbook 分级推理排查 | **不做** | 推理链是炫技，一线要的是答案不是教程 | 永不单独做，并入错误码 solution 字段 |
| 关单沉淀流水线（脱敏/改写/挂节点/审核） | **不做自动化** | 流水线没跑通就是脏数据。这版由主管每周人工补 5 条 | MVP 验证通过后第二版第一个做 |
| 质量管控智能体（置信度打分/话术合规/复核闭环） | **只留一条硬规则** | 完整 QC 是周频后台活，不值得这版投入 | 第二版 |
| 升级包自动生成 | **不做** | 一线每周才遇到几次，手动写邮件更快 | 不做 |
| 知识缺口挖掘/健康巡检/数据看板 | **不做** | 主管周频功能，不是一线日频 | 第二版 |
| LangGraph 三 Agent 编排 | **降级** | 简单查询就是"检索→LLM 生成"两步，画三个 Agent 是架构炫技 | 不做 |
| SSE 流式渲染 | **可选** | 薄版 2–3 秒同步返回完整结果即可，流式增加复杂度 | 延迟不达标再上 |
| iframe 嵌入工单系统右侧栏 | **不做** | 依赖工单系统开放能力，周期长；先用浮层绕开 | 第二版 |
| 新人培训/题库/独立问答框 | **继续不做** | 沿用 v2 已砍结论 | 不做 |

## 四、一线日常使用流程（核心链路越短越好）

```
在工单系统里读到客户问题
  → 按快捷键（如 Ctrl+Space）唤起浮层
  → 粘贴客户原话（或直接输入错误码）
  → ≤3 秒内浮层显示：
       ① 错误码释义与触发条件（命中时）
       ② 3 条相关历史工单的解法摘要（带来源工单号）
       ③ 一段可直接复制的对外答复草稿（已带上客户版本号）
       ④ 若证据不足：显示"未找到可靠依据，建议转二线"，不给草稿
  → 一键复制草稿 → 切回工单输入框粘贴 → 发出
卡住 → 手动转研发（不做升级包）
```

**衡量标准**：从唤起浮层到复制草稿，全程不超过 5 秒。任何一个环节让人多操作一步，就砍掉那个环节。

## 五、技术选型（务实降级版）

| 层 | 选型 | 说明 |
|----|------|------|
| 后端 | Python 3.10 + FastAPI + Uvicorn | 保留 |
| 编排 | **线性 pipeline**（`retrieve → build_context → llm_generate`） | 不引入 LangGraph；一个函数调一个函数，出错好查 |
| LLM | DeepSeek Chat（或 Qwen） | 保留 |
| 向量检索 | BGE-small-zh + FAISS（或 SQLite + LIKE 兜底） | 只用于历史工单相似召回，不做混合检索/RRF/时间权重那一套 |
| 结构化查询 | MySQL/PostgreSQL 直接索引查询 | 错误码查询走精确索引，<100ms 不是难事 |
| 前端 | **Tampermonkey 油猴脚本 + 一个浮层 HTML**（或 Vue3 单页应用挂在工单系统页面上） | 这是本版关键：绕开工单系统 iframe 审批，最快让一线不离开工单页面 |
| 协议 | 普通 JSON POST 返回 | 不上 SSE；3 秒内出结果即可 |
| 部署 | docker-compose（backend + db），一个进程 | 不搞 nginx/gzip/SSE 那套 |
| 埋点 | query_log 表记录每次查询、复制、点踩 | 不上独立监控栈 |

**性能目标（只卡死两条）**：
- 错误码精确查询 P95 < 0.5 秒（结构化索引本就该这么快）
- 粘贴问题到出草稿 < 3 秒（含 LLM）

## 六、数据模型（只保留真正用到的表）

| 表 | 关键字段 | 用途 |
|----|---------|------|
| `error_code` | code(PK), name, meaning, trigger_condition, known_causes[], solution, related_versions[], updated_at | **P0-1 核心，这版人工填准 30–50 条** |
| `customer_asset` | customer_id(PK), plan, version, enabled_modules[], key_configs[], recent_changes[] | 给草稿自动带客户版本 |
| `ticket_history` | ticket_id(PK), customer_id, raw_text, solution_text(脱敏), created_at | 脱敏导入 ≥100 条，做相似召回 |
| `query_log` | id, query, error_code_hit, customer_id, latency_ms, copied, thumbs_down, created_at | **算账用，唯一不能省的表** |
| `user` | 极简：工号、姓名、角色（一线/主管） | 鉴权够用即可 |

**删除**：runbook 复杂结构、escalation、knowledge_gap、reply_template、field_permission 行级权限（本版试点范围小，用部署环境隔离代替复杂权限模型）。

## 七、接口（四个就够）

| 接口 | 方法 | 说明 |
|------|------|------|
| `/api/lookup?code=XXX` | GET | 错误码秒查（P0-1） |
| `/api/draft` | POST | 入参：`{ raw_text, customer_id? }`；返回：`{ error_code?, evidence_summaries[], draft, confidence: "high"|"low" }`；`confidence=low` 时不返回 draft |
| `/api/tickets/{customer_id}/context` | GET | 客户版本/模块/最近变更，供浮层小卡片展示 |
| `/api/feedback` | POST | `{ query_id, copied, thumbs_down }` |

## 八、排期（D0 验证 + D1–D5 开发）

| 阶段 | 时间 | 任务 | 退出条件 |
|------|------|------|----------|
| **D0** | 0.5–1 天 | 按第一章拉 ROI 数据，填验证表，做 go/no-go | 产出《ROI 验证记录表》；不达标则停 |
| D1 | 1 天 | 工程骨架（FastAPI + DB + docker）；**人工整理 30–50 条高频错误码入 `error_code` 表**；脱敏导入 ≥100 条历史工单 | 错误码表可查；历史工单能被向量召回 |
| D2 | 1 天 | `/api/lookup` 精确查询 + 客户上下文聚合；单元测试 | 错误码查询 <0.5s |
| D3 | 1.5 天 | `/api/draft`：检索相似工单 → 拼客户上下文 → LLM 生成草稿；**"无引用不输出"硬规则** | 给 30 条真实历史工单回放，人工评估草稿"能不能直接发" |
| D4 | 1 天 | Tampermonkey 浮层脚本：快捷键唤起、粘贴、显示三块、一键复制；埋点上报 | 在测试工单页面上完整走通"唤起→复制" |
| D5 | 0.5 天 | 修 bug；找 2–3 个一线同事实际用半天；根据吐槽改 | 试点同事当天主动用了 ≥3 次 |

> 总共 **5–6 个工作日**。任何一天任务没完成，**砍功能不砍工期**——优先保 P0-1，其次保 P0-2 的"无引用不输出"。

## 九、验收标准（只看一线真用了）

### 9.1 功能验收（硬卡）

- [ ] 错误码查询 P95 < 0.5s
- [ ] 粘贴问题 ≤3 秒返回草稿
- [ ] **无引用硬规则生效**：故意问一个知识库里没有的问题，系统必须回答"未找到可靠依据"，且不输出草稿
- [ ] 草稿中出现的每个事实都能在 evidence_summaries 里找到来源
- [ ] 浮层在真实工单系统页面上能唤起、能复制

### 9.2 业务验收（这才是"值不值"的答案，用一周试点数据）

| 指标 | 达标线 | 怎么测 |
|------|--------|--------|
| 试点使用率 | 3 个同事 × 3 个工作日，人均主动唤起 ≥5 次/天 | 查 `query_log` |
| 草稿可直接发率 | ≥ 50% | 试点期间随机抽 20 条草稿，问当事人"复制后改了多少字"；改了 ≤2 句算"可直接发" |
| 点踩率 | < 20% | `query_log.thumbs_down` |
| 主观省时反馈 | 至少 2 人明确说"今天查错误码/写回复省了时间" | 口头问，不用问卷 |
| 无引用误伤率 | < 10% | 试点期间"未找到依据"的回答里，事后看其实是知识库里有的比例 |

### 9.3 不达标怎么办

- 使用率不达标 → 先查入口（浮层唤不起？太慢？找不到？），**不要加新功能**。
- 草稿可直接发率低 → 查是不是冷启动数据太少，补错误码库和历史工单，不要急着上 LLM 新模型。
- 用一周后两项仍不达标 → 项目终止，错误码速查页保留给一线，损失可控。

## 十、冷启动数据（决定草稿敢不敢发）

这是整个 MVP 最不能省的一步：

1. **错误码库（人工填）**：找一个二线工程师，花半天把过去一年出现 ≥3 次的错误码整理进 `error_code` 表，每个码写清楚"是什么、什么时候触发、已知解法"。这张表是 P0-1 的全部价值，也是草稿的最高质量证据。
2. **历史工单（脱敏导入）**：导出 ≥100 张已解决工单，去掉客户姓名/联系方式/公司名，保留"客户原话 + 最终解决方案"，向量化入库。
3. **客户资产（导入）**：只需要版本号、开通模块、最近一次变更三类字段，够草稿写"贵司当前版本"即可。
4. **禁止**：用 ChatGPT 编演示工单、编错误码。假数据第一周就会被一线戳穿。

## 十一、MVP 通过后才谈的第二版

只有当第九章业务验收全部达标，才进入下一阶段，按这个顺序做：

1. 关单沉淀半自动流水线（人工审核候选池，不允许自动入库）
2. 相似工单"解决效果"加权排序
3. 主管侧：知识缺口榜单 + 处理时长/草稿采纳率周报（一张表，不做 ECharts）
4. 真实工单系统 iframe 嵌入（等数据够硬再去谈系统对接）
